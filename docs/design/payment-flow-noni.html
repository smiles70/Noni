0.1 Known defects gating parts of this flow

D1 — Gift code lost in live Stripe mode. Stripe redirects back to STRIPE_SUCCESS_URL?cs={CHECKOUT_SESSION_ID} only; the gift_token, is_gift, and purchase params the mock flow relies on are dropped. The buyer pays but never sees the gift code. No email is sent (no email system exists). Gift sales are blocked until fixed.
D2 — Gift price never charged. create_checkout always uses the single STRIPE_PRICE_ID_MODULES_4_5 price regardless of is_gift. A $59 gift price in Stripe would be ignored without a code change.
D3 — Success page shows no product details in live mode (cosmetic): the confirmation card renders an empty product name because Stripe's redirect carries no product params.

3. B2C Stripe flow (PAYMENT_PROVIDER=stripe) — target state

Two important corrections vs. earlier drafts: (a) all endpoints are under /api/v1/ — the legacy /api/billing/... paths return 302 redirects, which Stripe's webhook sender does not follow; (b) the webhook is sent by Stripe's servers in parallel with the browser redirect — the success page does not trigger it. A Redis broker and a running Celery worker are required or the entitlement is never granted.

5. Refund flow (corrected)

There is no POST /api/billing/refund endpoint and none is planned for V1. Refunds are initiated by a human in the Stripe dashboard after a support request (ADR 0021: full refund within 30 days, no questions asked). The revocation happens through the same webhook + Celery path as purchases.
